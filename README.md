> Computational pipeline comparing classical Machine Learning (stacking ensembles) against a Graph Neural Network (ChemProp D-MPNN) for QSAR modeling of *TgDHFR* inhibitors, followed by ADMET profiling and structure-based virtual screening / molecular docking (AutoDock Vina) against PDB 6AOG.

This README documents how to reproduce every computational result in the manuscript, including expected runtimes, hardware assumptions, and known sources of numerical variation. It reflects the environment and pipeline as validated on 2026-09-21/23 (see "Reproducibility notes" below).

---

## 1. Repository structure

```
scripts/                 Pipeline steps (00 through 13), shared modules (paths_config.py, logger_utils.py, nb_stats.py, splits.py, gnn_utils.py)
run_pipeline.py           Orchestrator: runs all steps in order, or a subset (see below)
conda_environment.yml     Conda environment definition (Python 3.11, pip-managed dependencies)
requirements.txt          Pinned pip dependencies (see comments inside for rationale)
setup_env.sh              One-shot environment setup script
data/                     Input datasets (SMILES/pIC50 training set, TDC hERG/Caco-2 tables, FDA library)
receptor/                 Prepared receptor and crystal ligand (PDBQT) for docking
results/                  CSV/NPY/joblib outputs generated by the pipeline (git-tracked for auditability)
figures/                  PNG/PDF figures generated by the pipeline
latex/                    Auto-exported LaTeX \newcommand variable files, consumed by the manuscript
logs/                     Per-script logs plus a master_pipeline_<timestamp>.log for each full/partial run
```

`results/`, `figures/`, `logs/` and `latex/*.tex` are committed to the repository so that reviewers can inspect the exact outputs of the validated run without re-executing the pipeline, while still being able to regenerate them from scratch (see Section 4).

## 2. Environment setup

The pipeline was validated on Python 3.11.16 (Linux, 48 CPU threads, 248 GB RAM). It should run on fewer cores, at a proportionally longer runtime (see Section 5).

```bash
conda env create -f conda_environment.yml -n mlvsgnn_repro
bash setup_env.sh
```

`setup_env.sh` creates/updates the conda environment from `conda_environment.yml` (which in turn installs everything pinned in `requirements.txt`), then installs `PyTDC==0.4.1` separately with `pip install --no-deps` — PyTDC declares an old `rdkit-pypi` build as a dependency that would silently downgrade/duplicate the pinned RDKit if installed normally — and finally runs `python run_pipeline.py --check` to confirm every third-party module actually imports.

Key pinned versions (full list and rationale in `requirements.txt`; the complete resolved environment, including transitive dependencies, is captured in `requirements-lock.txt` via `pip freeze` on the validated workstation):

| Library | Version | Notes |
| :--- | :--- | :--- |
| RDKit | 2025.9.3 | Single installation; verify with `pip list \| grep -i rdkit` after setup (PyTDC must not add a second one) |
| scikit-learn | 1.6.0 | Classical ML / stacking ensembles |
| XGBoost / LightGBM | 3.1.2 / 4.6.0 | Stacking base learners |
| PyTorch / Lightning | 2.5.1 / 2.6.5 | ChemProp backend (CPU only in this configuration) |
| ChemProp | 2.2.4 | D-MPNN GNN baseline (v2 API) |
| AutoDock Vina (Python bindings) | 1.2.7 | Molecular docking |
| Meeko / Gemmi | 0.8.0 / 0.7.5 | PDBQT ligand preparation (Meeko requires Gemmi at import time even though it is not declared as a dependency) |
| PyTDC | 0.4.1 | ADMET oracles (hERG, Caco-2); installed with `--no-deps`, see above |

**Not used / intentionally removed:** DGL, DGL-LifeSci and the AttentiveFP baseline were removed from this pipeline. DGL 2.1.0 (the last version with prebuilt wheels at the time of writing) does not support PyTorch 2.5.1, and there is no compatible combination that also satisfies ChemProp's requirements. ChemProp (D-MPNN) is the only GNN baseline reported.

**System dependency (optional):** `obabel` (OpenBabel) is only required by `scripts/prep_receptor.py`, which is **not** part of the `run_pipeline.py` sequence. It is only needed if you want to regenerate `receptor/receptor.pdbqt` and `receptor/crystal_ligand.pdbqt` from the raw PDB structure. Since both prepared files are already tracked in `receptor/`, most users will not need to install it.

```bash
sudo apt-get update && sudo apt-get install openbabel libxrender1 libxext6   # only for prep_receptor.py
```

## 3. Running the pipeline

```bash
python run_pipeline.py --list            # show all 24 steps in execution order
python run_pipeline.py --check           # verify every dependency actually imports (no computation)
python run_pipeline.py                   # run everything: main analysis (00 -> 09), outlier sensitivity (S01, S02, 10), scaffold-split robustness (SC01, SC09, 13), then the figure stage
python run_pipeline.py --from 05         # resume from step 05 onward (e.g. after an interruption)
python run_pipeline.py --only 07 07.1    # run only the listed steps
python run_pipeline.py --no-sensitivity  # skip the with-extreme-values re-run
python run_pipeline.py --no-scaffold     # skip the scaffold-split re-run (SC01, SC09, 13)
python run_pipeline.py --only figures    # rebuild every figure and table from existing results (seconds, no recomputation)
```

Each run writes a master log to `logs/master_pipeline_<timestamp>.log` in addition to each script's own `logs/<script>.log`. On a non-zero exit code the pipeline halts immediately; re-run with `--from <step>` after fixing the issue rather than restarting from scratch.

For long unattended runs (e.g. over SSH), use `tmux` or `nohup` — step 01 alone takes on the order of hours (see below).

Hardware profile and parallelism are controlled via environment variables read by `scripts/paths_config.py`:

```bash
export MLGNN_PROFILE=workstation   # default; see paths_config.py for available profiles
export MLGNN_N_JOBS=8              # override the number of threads (default: min(profile setting, os.cpu_count()))
```

## 5. Reproducibility notes

Every step uses a fixed random seed (`RANDOM_STATE = 42` in `paths_config.py`, propagated to scikit-learn, XGBoost, LightGBM, PyTorch/Lightning `seed_everything`, and AutoDock Vina's `seed` parameter). Despite this, a small amount of run-to-run numerical variation is expected and has been characterized empirically:

- **Step 04 (baseline, feature selection, augmentation):** every model of this step is fitted single-threaded and the parallelism is applied across independent tasks (features in the permutation importance, runs of the 5-run ensemble), so the results do not depend on the number of workers. The cause of the earlier run-to-run differences was identified: a multi-threaded `RandomForest.predict()` sums the trees in a thread-dependent order, which changes the last bits of the predictions, and the old selection rule `importance > 0` then flipped the ~750 features whose importance is zero up to floating-point noise (about 1e-15; the smallest genuine importances are about 1e-7). Two executions of the old code retained 1389 and 1826 bits of the same split. The selection now keeps features with importance above `IMPORTANCE_TOL = 1e-9` and the fits use `n_jobs=1`; permutation importances computed with 46 and with 8 workers were bitwise identical and retained the same 1255 bits.
- **Ensemble of runs (step 04):** the 5 runs of the ensemble now use different seeds for the tree ensembles (`RANDOM_STATE + run`). Previously the reseeding was never applied (the stacking object has no `random_state`), so the 5 runs were identical copies.
- **Redocking validation (step 06) and docking (step 07):** deterministic given the fixed Vina seed (42); centroid distance for the redocking control reproduced at 0.317 Å (threshold: 2.0 Å) across repeated runs.
- **ChemProp / GNN (step 09):** PyTorch/Lightning training on CPU with multiple threads is not bit-reproducible even with a fixed seed, for the same floating-point non-associativity reason as above. Repeated 5x5 CV runs agree to about the third decimal rather than to the last one (observed mean fold R² between 0.725 and 0.729 across three executions on the current data set).

If you reproduce this pipeline on different hardware, expect small variation in the GNN's R², but not in the qualitative conclusions reported in the manuscript.

## 7. Docking setup

Docking targets the DHFR active site of PDB 6AOG. The screening box is centered on chain B specifically (not the average of both chains, which was found during redocking validation to be offset from the true active site — see `latex/redocking_variables.tex` and the `[IMPORTANT WARNING]` printed by `scripts/06_redocking_validation.py`). `CENTER_X/Y/Z` in `paths_config.py` must match the value step 06 reports; the pipeline checks this consistency automatically and reports the offset (validated at 0.001 Å).

## 8. Outputs

- `results/*.csv`, `results/*.npy`, `results/*.joblib` — numerical results and fitted models consumed by later steps.
- `figures/*.png`, `figures/*.pdf` — all manuscript figures, regenerated by the `*.1_build_figures.py` steps.
- `latex/*.tex` — `\newcommand` variable definitions consumed directly by the manuscript LaTeX source, so that numbers in the paper stay in sync with the last pipeline run.
- `sensitivity/{results,latex,figures,logs}/` — outputs of the outlier sensitivity re-run (steps S01/S02); the main outputs are never overwritten. The comparison lands in `results/10_outlier_sensitivity.csv`, `results/10_outlier_diagnostic.csv` and `latex/outlier_variables.tex`.
- `logs/` — one log per script plus a timestamped master log per pipeline invocation.
